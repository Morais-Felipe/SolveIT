<context>
- O 07-01 entregou o `docker-compose` (API + web/nginx + MySQL + Mailpit). É contra ele que o E2E roda: mesmo build de produção, mesmo proxy `/api`, mesmo SMTP falso.
- Fluxo do chamado: ABERTO → (assumir) EM_ANDAMENTO → RESOLVIDO (atendente responsável ou ADMIN) → FECHADO (solicitante dono).
- O primeiro ADMIN só nasce pelo SQL protegido de `docs/PRIMEIRO-ADMIN.md`, que exige `admins_ativos = 0`. Por isso o E2E precisa de um banco **vazio** a cada execução.
- O Mailpit publica a porta 8025 fixa: hoje dois compose ao mesmo tempo colidiriam.
- Auditoria rápida já feita: todas as páginas com dados têm carregando, vazio e erro; o achado conhecido é o menu do ADMIN no celular, em que "Categorias" fica escondido numa faixa de rolagem horizontal sem indicação.
- 241 testes de back-end (17 classes de integração MVC com MySQL real, 7 de serviço/concorrência, testes de notificação) e testes de componente do front-end. A revisão de escopo de 2026-10-30 definiu que a matriz de autorização (QUAL-03) é a desses testes, não uma nova.
</context>

<risk>
- **E2E instável (flaky):** testes de navegador falham por timing. Mitigação: só esperas baseadas no que o usuário vê (`getByRole`, `expect(...).toBeVisible()`), nunca `sleep`; jornadas em série; rastro (trace) salvo quando falha.
- **Apagar dados de desenvolvimento por engano:** o E2E derruba e recria o banco. Mitigação: ele usa um projeto compose separado (`solveit-e2e`, portas 8180/8125), nunca o `solveit` do dia a dia.
- **CI mais lento:** o E2E constrói as duas imagens (~5–8 min). Ver D-4.
</risk>

<decisions-for-approval>
- **D-1 Playwright dentro de `solveit-web/e2e/` (recomendado):** `@playwright/test` como devDependency do front-end, só com o Chromium (download de ~150 MB na primeira vez). Arquivos `*.e2e.ts`; o Vitest passa a olhar apenas `src/`, então `npm test` continua sendo só testes de componente. Alternativa: pacote separado na raiz, descartada por duplicar Node/lint/tipos.
- **D-2 Ambiente isolado e descartável (recomendado):** `npm run e2e` sobe `docker compose -p solveit-e2e` com `SOLVEIT_WEB_PORT=8180` e `SOLVEIT_MAILPIT_PORT=8125`, roda os testes e derruba com `down -v`. Para isso o compose ganha a variável da porta do Mailpit (padrão 8025, nada muda para quem já usa). O `.env` com segredos de teste é gerado na hora, fora do Git.
- **D-3 Primeiro ADMIN pelo procedimento documentado:** a preparação do E2E cadastra o ADMIN pela API e executa, via `docker compose exec mysql`, o mesmo SQL protegido de `docs/PRIMEIRO-ADMIN.md` (com `admins_ativos = 0` verificado). Nenhuma rota ou atalho novo na aplicação.
- **D-4 E2E também no GitHub Actions (recomendado):** novo workflow `e2e.yml` em todo PR para a `main` (sobe o compose no runner, que já tem Docker) e salva o relatório do Playwright quando falha. É a prova visível de QUAL-05 no portfólio. Alternativa: só local antes da entrega, com o PR mais rápido.
- **D-5 Três jornadas, em desktop e celular:** a suíte roda em dois "projetos" do Playwright: desktop (1280 px) e celular (Pixel 7, 412 px), com usuários próprios por projeto.
  1. **ADMIN:** entra, transforma um usuário em atendente, cria uma categoria, vê o dashboard.
  2. **Solicitante:** cadastra-se pela tela, entra, abre chamado na categoria nova, comenta.
  3. **Atendente:** assume pela fila, resolve; o solicitante fecha; histórico e dashboard refletem.
  Mais duas checagens: o e-mail de chamado assumido chega ao Mailpit (consultado pela API dele), e um solicitante que chama uma rota de ADMIN **direto na API** recebe 403, provando WEB-07 ("sem depender da interface").
- **D-6 Menu do celular quebra em linhas (recomendado):** no celular os itens passam a quebrar linha (`flex-wrap`) em vez de rolar na horizontal: com 4 itens curtos ficam 2 linhas, todos visíveis. A jornada do ADMIN no celular clica em "Categorias" pelo menu, provando a correção. Alternativa: menu hambúrguer, descartada por exigir componente e estado novos para 4 links.
- **D-7 Mapa de evidências honesto (`docs/EVIDENCIAS-QUALIDADE.md`):** para QUAL-01, QUAL-02 e QUAL-03, uma tabela critério → classe de teste → o que prova. Matriz de autorização: endpoint × perfil/dono/responsável, cada célula apontando o teste que cobre a recusa ou a permissão. Onde o QUAL-01 pede "unitário" e a prova é de integração MVC com MySQL (escolha deliberada da revisão de escopo), o mapa diz isso. **Lacunas de autorização encontradas recebem teste neste plano; lacunas que não sejam de segurança ficam anotadas, sem teste novo.**
</decisions-for-approval>
