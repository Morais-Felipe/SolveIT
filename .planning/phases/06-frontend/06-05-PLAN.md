<objective>
O administrador acompanha a operação pelo dashboard e administra usuários (criar, editar dados, mudar perfil/ativo) e categorias (criar, editar, ativar/desativar). O atendente também vê o dashboard, no escopo que a API já calcula para ele.
</objective>

<api-contract>
- Dashboard: `GET /api/dashboard/resumo` (ADMIN e ATENDENTE). Resposta: `totais { aberto, emAndamento, resolvido, criticaAberta }`, `porCategoria[] { categoriaId, nome, quantidade }`, `cargaPorAtendente[] { atendenteId, nome, emAndamento }`, `abertosPorPrioridade { BAIXA..CRITICA: n }`. O escopo por perfil é do servidor (05-01).
- Usuários (só ADMIN):
  - `GET /api/usuarios?page&size` (máx. 100; sem filtros).
  - `POST /api/usuarios` `{ nome, email, senha, perfil }` → 201. E-mail repetido: 409 `EMAIL_ALREADY_REGISTERED`.
  - `PUT /api/usuarios/{id}` `{ nome, email, senha?, versaoEsperada }` (só dados pessoais; enviar `perfil`/`ativo` dá 400).
  - `PATCH /api/usuarios/{id}/operacao` `{ perfil, ativo, versaoEsperada }` → `{ usuario, chamadosDevolvidos }`. Sem mudança: 409 `INVALID_STATE`. Último ADMIN ativo: 409 `LAST_ACTIVE_ADMIN`. Atendente que deixa de atender devolve seus chamados EM_ANDAMENTO à fila.
  - Versão desatualizada em qualquer escrita: 409 `STALE_RESOURCE`.
- Categorias:
  - `GET /api/categorias?page&size` — **hoje devolve só as ativas, para qualquer perfil.**
  - `POST` `{ nome, descricao? }`, `PUT /{id}` `{ nome, descricao?, versaoEsperada }`, `PATCH /{id}/ativo` `{ ativo, versaoEsperada }` (só ADMIN). Nome repetido: 409 `CATEGORY_NAME_ALREADY_EXISTS`.
</api-contract>

<gap>
Sem ver as categorias inativas, o ADMIN não consegue reativá-las pela interface: a API só lista ativas. A correção mínima é no back-end (decisão D-1).
</gap>

<decisions-for-approval>
- **D-1 Listar categorias inativas (recomendado: parâmetro opcional):** `GET /api/categorias?incluirInativas=true`. Sem o parâmetro, comportamento atual (formulário de novo chamado não muda). Com o parâmetro, só ADMIN; outro perfil recebe 403, decidido no service (a autorização fica no servidor). Teste MVC cobre ADMIN, SOLICITANTE e ATENDENTE. Alternativa: rota separada `/api/categorias/todas`; descartada por duplicar paginação.
- **D-2 Dashboard em cards e tabelas (revisão de 2026-10-30):** quatro cards de totais (Abertos, Em andamento, Resolvidos, Críticos abertos), tabela "Abertos por prioridade", tabela "Por categoria" e tabela "Carga por atendente" (esta só aparece se a API devolver itens). Sem biblioteca de gráficos. Cada card de status leva à lista de chamados já filtrada (`/chamados?status=...`).
- **D-3 Usuários em tabela paginada (20 por página)** com nome, e-mail, perfil, situação. Ações por linha: "Editar dados" e "Perfil e situação", cada uma num painel próprio — espelha as duas rotas da API. "Novo usuário" abre o formulário de criação.
- **D-4 Confirmação ao desativar ou tirar perfil de atendente:** o painel "Perfil e situação" avisa que os chamados em andamento do atendente voltam para a fila; após salvar, a tela mostra "N chamados voltaram para a fila." usando `chamadosDevolvidos`. Não há prévia da quantidade (revisão de escopo: sem prévia).
- **D-5 O ADMIN não consegue se desativar acidentalmente?** A API protege apenas o *último* ADMIN ativo. Proposta: na própria linha, desabilitar "Perfil e situação" para o usuário logado, evitando que ele perca o acesso no meio da sessão. Se preferir permitir, a API continua como autoridade.
- **D-6 Conflitos com mensagem clara:** `STALE_RESOURCE` → "Outra pessoa alterou este registro. Recarregamos os dados; revise e tente de novo." (recarrega a linha). `LAST_ACTIVE_ADMIN`, `EMAIL_ALREADY_REGISTERED`, `CATEGORY_NAME_ALREADY_EXISTS` mostram a mensagem do servidor no campo/painel correspondente.
- **D-7 Categorias numa tabela com filtro "Ativas / Todas"** (usa D-1), ações Editar e Ativar/Desativar (um clique, reversível).
</decisions-for-approval>
