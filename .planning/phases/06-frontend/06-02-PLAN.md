<objective>
O solicitante vê seus chamados em uma lista paginada, filtra por status, prioridade e categoria, e abre um novo chamado.
</objective>

<api-contract>
- `GET /api/chamados?status&prioridade&categoriaId&page&size&sort` → `Pagina { items: Detalhe[], page, size, totalElements, totalPages }`. O servidor já restringe o solicitante aos próprios chamados; o front-end não envia `solicitanteId`.
- `GET /api/categorias?size=100` → categorias ativas (para o filtro e o formulário).
- `POST /api/chamados` (só SOLICITANTE) com exatamente `{ titulo, descricao, prioridade, categoriaId }` → 201 + `Detalhe`. Campos extras são rejeitados com 400.
</api-contract>

<decisions-for-approval>
- **D-1 Filtros na URL (recomendado).** Status, prioridade, categoria e página ficam em `?status=ABERTO&page=1` via `useSearchParams`. Recarregar ou compartilhar o link mantém a vista; o botão Voltar funciona. Alternativa: estado local (mais simples, perde-se ao recarregar).
- **D-2 Sem biblioteca de cache de dados.** Busca com `useEffect` + `AbortController` (cancela a requisição anterior quando o filtro muda). TanStack Query fica para quando houver repetição real.
- **D-3 Após abrir o chamado:** redirecionar para `/chamados` com aviso de sucesso. O detalhe (`/chamados/:id`) chega no 06-03; até lá, os itens da lista não são links.
- **D-4 `/chamados` para outros perfis:** a mesma página serve a ATENDENTE e ADMIN (a API devolve o escopo de cada um), mas o botão "Abrir chamado" só aparece ao SOLICITANTE.
</decisions-for-approval>
